History tab — chat view

A proposal for the session's History tab. It reads like a chat: what you asked sits on the right, what the agent answered on the left, and the agent's Markdown is rendered. Tool calls between two answers fold into one quiet card you open when you want the detail. It uses the same data the History tab reads today (the transcript endpoint's entries), so nothing new is required from the server to ship it. Every frame is live: open the cards, toggle tools, search.

1 · Running session · desktop

The newest messages sit at the bottom. While the session runs, a quiet "Working" line shows that the agent is between turns. Hover an answer to copy its Markdown or a link to it. In the dark frame the reader has scrolled up and three new entries arrived, so a "Jump to latest" pill appears.

Dark · scrolled up, 3 new below

  1. Person turn .turn[data-who=person]: a right-aligned bubble in the signal wash. The text is Markdown too, since people paste code and lists.
  2. Agent turn .turn[data-who=agent]: no bubble, full width up to a 50rem reading column, rendered with the system's .prose. Consecutive assistant entries without tools between them merge into one turn.
  3. Tool activity .activity: every tool_use and tool_result between two turns becomes one card. The card shows the count, the tool names, and a red flag when a call failed. Open it to see each call paired with its result; open a call to read its input and output in mono.
  4. System .sys: a small centred pill, such as "Session resumed" or "Context compacted".
  5. Day divider .day between entries on different days. Times show as HH:MM beside the speaker, the full timestamp in the tooltip.
  6. Long answers fold at 18rem with a "Show all" button, like the Conversation tab's data-clamped.

2 · The bar: tools on or off, and search

"Show tools" off leaves only the conversation between you and the agent. A failed call still leaves a small red marker so failures never disappear. Search highlights matches in the loaded entries and steps through them with Enter. The choice to show tools is remembered per browser.

3 · What the agent's Markdown renders to

Agents answer in GitHub-flavoured Markdown: headings, lists, task lists, tables, quotes, fenced code and inline code. Code blocks get the language label and a Copy button. A path/to/file.go:42 in inline code is tinted as a path, a natural hook for linking into the Code tab later. Raw HTML in the text is shown as text and never run.

5 · How each transcript entry maps

Entry kindShown asNotes
userPerson turn, right bubbleMarkdown rendered. Text the harness injected, such as a task-update turn, keeps the person style with a "harness" label.
assistantAgent turn, proseMarkdown rendered. Adjacent assistant entries merge into one turn.
tool_useA call row inside the activity cardThe tool name and the one-line summary from the server.
tool_resultThe output of the call above itPaired in order with the open call of the same tool. A result with no call becomes its own row. is_error gives the red mark and flag.
systemCentred pillPlain text.
truncated"Cut at 16 KiB" note under the textUnchanged from today.
  1. Markdown rendering is the one real choice. Option A: the browser renders it with a small vendored renderer in web/third_party, escaping raw HTML. Option B: the server renders it with the goldmark setup the documents already use and adds an html field to each entry. B keeps one Markdown look across the app but changes the transcript contract, so it goes through the architect.
  2. Pairing calls with results works by order today. An optional tool_use_id on both kinds would make parallel calls pair exactly. That would be an additive contract change.
  3. Unchanged behaviour: Load older at the top, polling with after= every 2 s while visible, a log region that the keyboard can scroll, windowing for long conversations.
